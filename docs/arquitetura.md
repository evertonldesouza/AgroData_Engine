# Arquitetura

> Documento técnico do AgroData Engine. Para o "porquê" de cada escolha, veja os
> [ADRs](./adr/).

## 1. Visão geral

O sistema tem três módulos que se comunicam por dois contratos estáveis: a
**tabela `Commodities`** (escrita pelo Python, leitura pelo .NET) e a **API REST**
(consumida pelo React).

```text
┌───────────────────────┐        ┌───────────────────────┐        ┌───────────────────────┐
│      Data Engine      │        │          API          │        │       Dashboard       │
│       (Python)        │        │        (.NET 10)      │        │    (React 19/Vite)    │
│                       │        │                       │        │                       │
│ collect → validate    │ INSERT │  Controllers          │  JSON  │  polling 15s          │
│ → persist → analyze   │───────▶│  → Application        │◀───────│  histórico via /history│
│ cron: 1×/hora         │        │  → Domain ← Infra     │        │  lazy chart           │
└───────────────────────┘        └───────────┬───────────┘        └───────────────────────┘
                                             │
                                             ▼
                              ┌──────────────────────────────┐
                              │ PostgreSQL (Supabase)        │
                              │ Commodities                  │
                              │  Id · Symbol · Price         │
                              │  Timestamp · Source          │
                              └──────────────────────────────┘
```

Nenhum módulo depende do processo de outro: o banco é o ponto de desacoplamento e a
API é a única porta de leitura do frontend. Isso permite evoluir cada parte e
implantá-la de forma independente (GitHub Actions para o Python, Render para a API,
GitHub Pages para o dashboard).

## 2. Camadas do backend

```text
AgroData.API ──────────▶ AgroData.Application ──────────▶ AgroData.Domain
      │                          ▲
      └──────▶ AgroData.Infrastructure ─┘
```

| Projeto | Contém | Não pode depender de |
| --- | --- | --- |
| `AgroData.Domain` | `Commodity`, `TrendDirection`, `ICommodityRepository` | nada |
| `AgroData.Application` | DTOs, `ICommodityService`, `CommodityService`, `TrendCalculator` | EF Core, ASP.NET Core |
| `AgroData.Infrastructure` | `AppDbContext`, `CommodityConfiguration`, `CommodityRepository`, migrations, health check | controllers |
| `AgroData.API` | Controllers, Problem Details, CORS, rate limiting, Swagger, health endpoints | nada além das camadas internas |

A regra prática: **Application define contratos, Infrastructure os implementa, API
apenas traduz HTTP**. Regras de preço (`TrendCalculator`) não conhecem banco nem
framework, por isso são testadas com casos de tabela puros.

## 3. Ciclo de vida de uma requisição

`GET /api/commodities/history?symbol=SOJA&points=60`

1. `RateLimiter` aplica o limite de 120 req/min por IP (`[EnableRateLimiting]`).
2. `CommoditiesController` valida o parâmetro e delega ao `ICommodityService`.
3. `CommodityService` normaliza o símbolo, limita `points` a 500 e consulta o
   repositório, propagando o `CancellationToken`.
4. `CommodityRepository` executa uma consulta `AsNoTracking` usando o índice
   `IX_Commodities_Symbol_Timestamp`.
5. O serviço ordena cronologicamente, calcula a média móvel de 7 pontos
   (`TrendCalculator.MovingAverage`) e monta o DTO.
6. Se nada for encontrado, o controller devolve `404` com `ProblemDetails`.
   Exceções inesperadas caem no `GlobalExceptionHandler`, que loga uma única vez
   com `traceId` e devolve `500` no formato RFC 9457.

## 4. Modelo de dados

```sql
CREATE TABLE "Commodities" (
    "Id"        integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "Symbol"    text        NOT NULL,
    "Price"     double precision NOT NULL,
    "Timestamp" timestamptz NOT NULL,
    "Source"    text        NOT NULL
);

CREATE INDEX "IX_Commodities_Symbol" ON "Commodities" ("Symbol");
CREATE INDEX "IX_Commodities_Symbol_Timestamp" ON "Commodities" ("Symbol", "Timestamp");
```

As colunas são PascalCase porque o schema pertence ao **banco**, não a um ORM:
o Python mapeia os mesmos nomes (`models.py`) que o EF Core (`CommodityConfiguration`).
Renomear uma coluna exige mudar os dois lados e gerar migration — motivo pelo qual
o `Commodity` na camada Domain carrega um comentário explícito sobre isso.

Migrations são aplicadas com `dotnet ef database update` (nunca automaticamente no
startup, para não arriscar produção em um deploy).

## 5. Data engine

```text
Settings (pydantic) ─▶ collector (simulated | http)
                             │  PriceSample (validado)
                             ▼
                     pipeline: dedupe → persist (SQLAlchemy)
                             │
                             ▼
                     analytics: pandas + média móvel
```

- **Configuração falha cedo**: `DATABASE_URL` ausente, `DATA_SOURCE` inválido ou
  `DATA_SOURCE=http` sem URL abortam o processo com mensagem clara.
- **Isolamento de erro**: uma falha por símbolo gera um item em `report.errors` e
  não impede a gravação dos demais.
- **Idempotência opcional**: `--dedupe-window 1800` ignora cotações idênticas vistas
  nos últimos 30 minutos (protege execuções manuais repetidas).
- **Observabilidade**: `PipelineReport` (`inserted`, `skipped`, `durationMs`,
  `errors`) é o payload do `--json`, consumido pelo GitHub Actions.

## 6. Frontend

```text
useCommodities ──polling 15s──▶ GET /api/commodities
        │                            │
        │                            ▼
        │                     normalização (v3 + legado)
        ▼
usePriceHistory ──60s──▶ GET /api/commodities/history?points=N
        │
        ▼
mergeSeries → linhas alinhadas por minuto → MarketChart | HistoryTable
```

- O gráfico usa o **histórico real** do banco; o polling só atualiza os cartões.
- Falha de rede: backoff exponencial (15s → 120s), aviso "DEGRADED" e botão de retry.
- Aba oculta: o polling pausa e refaz a consulta ao voltar (`visibilitychange`).
- Recharts é carregado sob demanda (`React.lazy`), mantendo o bundle inicial em ~74 kB gzip.

## 7. Operação

| Item | Onde |
| --- | --- |
| Build da API | `Dockerfile` multi-stage, usuário não-root, healthcheck em `/health/live` |
| Banco local | `docker-compose.yml` (PostgreSQL 16 + API) |
| Deploy da API | `render.yaml` (health check em `/health/ready`) |
| Deploy do dashboard | `.github/workflows/cd-frontend.yml` (GitHub Pages) |
| Ingestão | `.github/workflows/data-pipeline.yml` (cron horário, `--dedupe-window`) |
| Qualidade | `ci-backend.yml`, `ci-frontend.yml`, `ci-data-engine.yml` |

## 8. Limites conhecidos

- A API é pública e somente leitura; não há autenticação ([ADR 0004](./adr/0004-public-read-only-api.md)).
- O plano gratuito do Render hiberna a API após inatividade: a primeira chamada pode
  levar alguns segundos (o dashboard mostra `DEGRADED` até responder).
- Cotações simuladas por padrão; o coletor HTTP existe e está testado contra um
  provedor falso, mas uma fonte pública real (ex.: CEPEA) ainda está no roadmap.
